# Observable requirements

## Scope and journey

Research all four sources before implementing any new production adapter. For each, record exact official roots, independent operator evidence, listing/detail boundaries, pagination, promotion classification, validity, participation and access constraints. Produce a four-column decision matrix and request ledger. A source may be blocked without registration or a placeholder adapter.

An operator can preview a justified adapter without a database. A shadow source must reject ingestion before DB/outlet operations. Only an enabled source with complete acquisition and complete verified facts may publish through the existing generic gate. Incomplete facts enter direct review; expired offers exclude before outlet lookup; corrected decisions and generic dedupe remain intact.

## Merchant rules

- FairPrice: start from promotions/catalogue roots. Ordinary/member product price is insufficient; explicit campaign/bundle/gift semantics are required. Product priceValidUntil is not campaign expiry. Never repair malformed JSON-LD into trusted facts. Product association and selected-store participation need exact evidence; online campaigns do not gain invented outlets.
- Kris+: acquire the public web promotion directory only. Operator ownership must cover that exact directory. Resolve or report load-more. Associate cards with exact public details and preserve partner merchant identity. App-only facts stay unknown; multi-merchant ambiguity remains review work.
- Dian Xiao Er: preserve one card/lightbox evidence boundary. Adjacent captions/terms/dates cannot leak. Image pixels and filenames cannot establish facts; clearly associated accessible text can. Duplicate identities or unresolved Wix loading fail completeness. Participation needs explicit campaign wording and an official directory.
- CS Foods: ordinary bounded fetch only. Stop adapter work when access controls block official pages. Attempt ownership independently. Product-sale metadata does not establish historical campaign identity or dates. Complete products and complete campaigns are distinct.

## Acceptance criteria

1. All four have separate ownership, acquisition, enumeration, classification, detail, participation, blocker and final-state records; no rankings.
2. Every implemented adapter has deterministic offline evidence/candidate/revision identities, isolated exact hosts and a bounded listing/detail boundary. Unknown pagination, duplicates and structural changes fail closed.
3. Enablement requires verified ownership, complete public acquisition/classification/association, safe campaign/merchant/participation semantics, offline replay and no source-level blocker; otherwise shadow or blocked as defined in intent.
4. New sources start with DEFAULT_LIMITS; only evidenced count-budget increases are allowed. Bytes, timeouts, redirects, DNS/SSRF and CLI limits remain unchanged.
5. Captures are append-only in separate merchant fixture roots, with requested/final URLs, timestamps, status/type/bytes/hash/purpose; retain useful failure diagnostics without cookies or private credentials.
6. Pepper seven, Pepper publish/update, Shake 4 exclude/5 review/1 ready and Parkway publish, Gourmet's three blockers, Paradise shadow, persistence/review/dedupe and legacy ingestion pass regression checks. Processor/schema remain unchanged.
7. Frozen merchant-map inputs and 139 rows are preserved. Changes are restricted to the four selected rows and aggregate counts; blocked sources show adapter=none and explicit blockers.
8. Enabled sources run captured disposable PostgreSQL/PostGIS checks with dispositions and replay metrics; shadow/blocked sources perform no DB/outlet operations.
9. Deliver research, implementation/verification evidence, exact changed files and protected-file hashes; no excluded operations occur.

Open source questions are research outputs, not assumed approvals. No product decision currently prevents bounded research.
