# Revision 6 design

Create immutable revision-6 protocol and registry assets by copying revision 5 and adding the frozen `research_role` classification. Pin exact SHA-256 hashes in the protocol loader, extend revision unions to `3 | 4 | 5 | 6`, validate exactly the three expected core source IDs for revision 6, and default only newly opened intervals to revision 6. Existing active intervals continue to select their pinned revision and hashes.

Keep revision-5 acquisition summarization unchanged. The revision-6 summary reads scheduled pass data and recovery artifacts and evaluates enumeration and extraction independently across the frozen core IDs and the full registry. Core content completeness requires complete listing enumeration for each core live observation window or strict recovery covering its failure/missed window. Semantic ambiguity and failed details remain extraction/review diagnostics and may produce recall misses; they do not remove an acquired listing from the denominator. Core cadence completeness remains based only on scheduled live core passes. All-registry fields retain the corresponding full 19-source health.

Candidate isolation must occur before primary review/scoring and must not use benchmark information. Because merged candidates currently keep top-level facts from the latest observation while only occurrences retain source IDs, preserve a source-specific candidate variant/evidence record during discovery merge. A reusable `projectCandidatesForSources(candidates, sourceIds)` reconstructs each candidate from retained source variants, filters occurrences to the selected source set, recomputes earliest receipt/provenance from those occurrences, and drops candidates with no selected-source evidence. This prevents supplemental top-level fields from leaking into core matching or fact scoring.

Add `evaluateRevision6()` alongside the existing revision-5 evaluator. It receives frozen candidates, Telegram benchmark/reviews and explicit core/all completeness inputs. It projects core and supplemental candidate views before scoring. Core replacement records and fact metrics are calculated only from the core projection; supplemental matching is a separate descriptive pass that can identify supplemental-only observations without changing primary assignments. Primary timing further filters to live core occurrences and live Telegram benchmark observations.

Add a separate revision-6 cumulative metric family. Do not combine revision-5 replacement recall with revision-6 core recall. The tracker uses revision-6 core replacement intervals for its initial >=3 gate, while retaining legacy and revision-5 metrics for historical reporting.

Service lifecycle uses the active interval's pinned revision during restart/reconciliation. Revision-5 and revision-6 observing intervals both use the existing recovery machinery; closing a revision-6 interval uses the new dual completeness summary. After an active revision-5 interval closes, the service reselects the requested/default revision 6 before opening the next interval. Sealed-evaluation validation checks each revision against the interval without reinterpreting older evaluations.

The tracker remains read-only. It reports runtime catch-up capability for all 19 sources, the rev6 registry role, proof/checkpoint/pagination details, core/full-registry completeness, supplemental failures, and supplemental-only matches. No recovery rule is relaxed and no production path is touched.

The [runtime repair](../rev6-runtime-completeness-repair/design.md) adds explicit enumeration/extraction diagnostics. Durable checkpoint means a dated, ordered archive observation with a proved terminal or checkpoint-overlap boundary, not any successful HTTP listing snapshot. Caps, required pagination, interruptions and loops prevent writes/advances. Invalid legacy runtime checkpoints are ignored on read without deleting them. Valid checkpoints drive live incremental traversal to the prior boundary plus exact URL/content-hash overlap and one deterministic extra page; deeper archive pages need not be exhausted. Bootstrap remains bounded and cannot claim continuity before a valid checkpoint.

September 30, 2026 is retained as implementation-transition evidence and intentionally excluded from formal rev6 analysis. `analysis.ts` filters it only in research cumulative/tracker analysis; it does not change captured evidence, frozen assets, interval reasons or evaluator results. October 1 is the earliest candidate repaired Singapore day, conditional on actual runtime activation and valid complete observations. No revision 7 is needed.

Implementation details confirmed during verification:

- Projections receive evidence-bound `cohort:<original-id>:<hash>` IDs. Existing full-candidate reviews cannot be reused. `acquisition.json` freezes `core_candidates` and `supplemental_candidates` alongside the full diagnostic acquisition; review primary files against `core_candidates`. `reviews/supplemental.json` optionally contains separate validity and match reviews; benchmark interpretation remains shared and independent.
- Fact scores remain manual adjudications against the frozen projection, not inferred from benchmark facts. Supplemental review IDs and scores never enter primary scoring. Missing legacy per-source evidence is conservatively omitted rather than attributed backwards.
- Timing conservatively excludes a core match if any retained core fact variant is catch-up or lacks explicit live provenance. A supplemental first receipt cannot move core timing earlier.
- The actual clean-day fixture exposed a blanket ConfirmGood category-route warning inherited from rev5. For the rev6 core entry only, the registered scope is the Deals archive, so that unrelated-category warning is not emitted. Real unresolved controls, truncation, listing failures and all recovery proof checks remain intact. Rev5 behavior is unchanged.
- Capability audit inspects frozen registry facts and current adapter code, not new live-network evidence. No supplemental source gained proven historical traversal; no adapter was promoted. Runtime audit exposes all nineteen outcomes.
